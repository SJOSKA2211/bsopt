# Research: Phase 4 - Ray Multi-Node Distribution & Optimization

**Date**: 2026-02-08

## 1. Executive Summary
The distributed training implementation (`src/ml/distributed_training.py`) utilizes `ray.train.torch.TorchTrainer` but instantiates `src/ml/trainer_v2.py:Trainer` which contains hardcoded single-process logic for MLflow logging and device placement.

## 2. Technical Context
- **`src/ml/distributed_training.py`**:
    - **Worker Function**: `train_func` (Line 32) is the entry point for Ray workers.
    - **Model Preparation**: Calls `ray.train.torch.prepare_model(model)` at Line 49.
    - **Trainer Instantiation**: Initializes `Trainer` at Line 61 inside the worker function.
    - **Orchestrator**: `BSOptDistributedTrainer` (Line 83) wraps `TorchTrainer`.
- **`src/ml/trainer_v2.py`**:
    - **MLflow Initialization**: `__init__` calls `mlflow.start_run()` at Line 42 unconditionally.
    - **Device Placement**: `__init__` moves model to device at Line 35: `self.model = model.to(device)`.
    - **Metrics Logging**: `_handle_epoch_end` logs metrics via `mlflow.log_metrics` at Line 82.
    - **Checkpointing**: `_save_checkpoint` saves `self.model.state_dict()` at Line 133.

## 3. Findings & Analysis
- **Execution Flow**:
    1. `BSOptDistributedTrainer.run` starts `TorchTrainer`.
    2. `TorchTrainer` spawns N workers executing `train_func`.
    3. Each worker executes `ray.train.torch.prepare_model`.
    4. Each worker instantiates `Trainer`.
    5. **Collision**: Each `Trainer` instance calls `mlflow.start_run()`, creating N concurrent runs for the same experiment.
- **Device Conflict**: `prepare_model` handles DDP device placement. `Trainer` subsequently calls `.to(device)`, which may be redundant or interfere with DDP wrappers.
- **State Dictionary**: `Trainer` saves `self.model.state_dict()`. If `model` is wrapped in DDP (from `prepare_model`), keys will be prefixed with `module.`.
- **Rank Awareness**: `Trainer` does not check for rank. All workers execute logging and checkpointing logic.

## 4. Technical Constraints
- **Ray Train**: Requires metrics to be reported via `ray.train.report` for aggregation on the head node.
- **MLflow**: Standard usage implies one run per experiment trial, not per worker.

## 5. Architecture Documentation
- **Current Pattern**: Monolithic Trainer trying to run inside a Distributed Worker.
- **Dependencies**:
    - `src/ml/distributed_training.py` depends on `src/ml/trainer_v2.py`.
    - `src/ml/trainer_v2.py` depends on `mlflow`, `torch`.
