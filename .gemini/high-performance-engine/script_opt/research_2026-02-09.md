# Research: Optimize Startup Scripts Logging and Error Handling

**Date**: 2026-02-09

## 1. Executive Summary
The startup scripts (`start_infra.sh`, `start_all_dev.sh`) utilize heavy output redirection (`> /dev/null 2>&1`), which masks critical failures during the infrastructure stabilization phase. While this provides a "cleaner" UI (printing dots), it makes debugging extremely difficult when services fail to start or stabilize.

## 2. Technical Context
- **Affected Component**: Startup Scripts
- **Current Behavior**: 
    - `check_health()` in `start_all_dev.sh` silences all stderr/stdout from `pg_isready`, `redis-cli`, and `rabbitmq-diagnostics`.
    - Ray startup/shutdown is silenced.
- **Related Files**:
    - `scripts/start_all_dev.sh`: Health check loop and Ray setup.
    - `scripts/start_infra.sh`: Container launch.

## 3. Findings & Analysis
- **Health Checks**: The `check_health` function is effectively a black hole. If a service is in a crash-loop, the script will wait for 30 seconds and then just say "Infrastructure failed to stabilize" without explaining why.
- **RabbitMQ**: The script doesn't currently check RabbitMQ health in the `check_health` function seen in the previous `read_file` (though `grep` shows it might be there in another version or I missed a line). 
- **Wait Loop**: The wait loop uses `sleep 1` and `printf "."`. This is "Jerry-level" UX.

## 4. Technical Constraints
- We want to keep the UI clean but provide verbose output on failure.
- Scripts must remain compatible with POSIX `sh` or `bash`.

## 5. Architecture Documentation
The scripts use a standard "Launch and Poll" pattern. Improvements should focus on "Launch, Poll, and Report" on failure.
